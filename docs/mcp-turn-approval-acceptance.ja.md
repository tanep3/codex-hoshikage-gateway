# MCPターン限定許可：受入と接続準備

2026-09-16。既存APIで実行できるGateway試験と、具体契約が必要な試験を分離する。本書の項目が存在するだけでは合格・配備済みを意味しない。

## 現契約で実行できる回帰試験

`cargo test --test mcp_interactions --test delivery --test approval_ui`

| 対象 | 検証内容 |
| --- | --- |
| 確認表示 | 原文を省略せず表示。実引数・コードと照合できない点と拒否・停止の操作を案内する |
| 明示操作 | 5件の承認は利用者が個別に回答するまでProxyへ送らない。表示改善だけで自動許可を開始しない |
| 集約 | 確認済みaccept + resolvedだけを同一依頼の1枚へまとめる。別依頼を数えない |
| 結果不明 | unknownや回答の証拠がないresolvedを成功として削除しない。後日の確実な照会では復旧できる |
| 削除復旧 | 削除失敗・作業終了・Gateway再起動が重なっても、未完了の整理を再開。カードや承認を再送しない |
| 表示revision | 古いPOST/PATCHの照合成功を、最新のカード内容の配信成功と扱わない |
| 既存操作 | 拒否・フォーム入力・世代変更・本人確認・旧ボタン・Serenityイベント変換の回帰 |

## 具体契約の照合項目（0.3で合意済み）

| 項目 | 決める内容 |
| --- | --- |
| Capability | 操作詳細・ターン限定許可の対応と上限、未対応時の応答 |
| 実行対応 | 1 Gateway依頼とProxyのResponse/Turn/依頼内容世代の照合。run_idが別に必要か |
| 操作情報 | call IDの根拠、安定したサーバー/ツール/設定世代、実引数・コード、秘匿・取得不能の表現 |
| 許可 | 作成・取得・一覧・取消のHTTP契約、表示revision・範囲fingerprint、TTL、監査 |
| 回答との原子性 | 現在の呼出しへの回答と後続許可の関係。片方だけ成功・結果不明の復旧 |
| Steer/停止 | 失効受付→内容世代更新→Steer送信の順序。停止/取消と自動適用の競合境界 |
| 復旧 | Proxy/Gateway再起動・設定変更・正式復元時の失効、照会保持期限、Idempotency-Key |
| 危険ツール | 常時個別確認対象、browser_evaluateを許可できる根拠と強制可能な制約 |

上表はAPI 0.3で合意済み。[Gateway詳細設計](mcp-turn-approval-gateway-design.ja.md)にHTTP・DB・表示・復旧を対応付け、接続実装へ進んだ。実サービスの受入結果とは区別する。

## 契約到着後の必須受入

1. 単発許可からターン限定許可へ昇格しない。後者は独立した本人の明示操作と範囲表示を伴う。
2. 同一Run・サーバー設定・ツール・依頼内容世代・範囲に一致する5回は1回の選択で進む。適用履歴で各callとの対応を確認する。
3. 同じツールでも別利用者・別チャット・別Run・並列Run・次の依頼には適用しない。
4. Steer受付の前後に呼出しを発生させ、旧許可を後続へ使わないことと順序の契約を確認する。承認ボタンは内容世代を変えない。
5. 停止・取消・Turn終了・期限切れ・設定変更・復元時の失効と、既に送信を開始した承認との競合を確認する。
6. 英語文面一致・到着順・同じ名前だけで紐付けない。call ID欠落・イベント欠落・識別不能では自動許可しない。
7. browser_run_code_unsafeは常時個別確認。browser_evaluateは実コード・権限を用いた実証とし、未実証の機能を閲覧専用と表示しない。
8. ツール内フォーム・認証URL・追加権限・秘密入力にターン限定許可を流用しない。
9. 許可作成/取消の前後で通信を切断・再起動し、同じキーの照会で復旧する。結果不明から別キーで再送しない。
10. 実MCPで操作内容→明示選択→実行→失効を確認し、実Discordでカードの件数とボタンを確認する。モック合格で実環境合格としない。

## 常駐環境への移行Gate

具体契約・上流対応付け・上記受入の結果を記録してから移行する。API未対応時は個別確認を維持し、常駐自動許可は有効にしない。先行UIの配備とターン限定許可の配備を別の記録にする。


## 合意0.3に対するGateway接続実装

操作詳細の本人限定表示、固定approval_context、fingerprint付き単発/ターン回答、許可一覧・取消照会、schema 7、エンドポイント上限を実装した。Mock試験では公開への実引数漏洩防止、古い表示/異なる実行への拒否、危険ツールのターン許可拒否、重複押下、取消応答喪失とApp再作成、schema 6からの既存対話保持を確認する。

未完了Gateは実Proxy/App Serverのcall対応・失効競合・並列Run隔離、実ブラウザの代替操作での確認回数、実Discordの表示と操作。特にbrowser_evaluateの連続確認削減を実現済みとはしない。Gatewayに許可判断の代行処理は追加せず、Proxyの適格性判定と明示選択を使用する。

## 常駐Proxyとの結合試験手順（2026-09-16）

本番GatewayのDBとは別の一時DBを使い、通常の受付・実行・MCP表示・回答処理を実Proxyへ接続する。Discord HTTPだけを試験サーバーへ向け、公開カードと本人限定詳細を分けて観測する。この試験はDiscord利用者の実ボタン操作を検証したことにはしない。

`tests/live_mcp_gateway.rs` は明示指定時だけ実行する。公開の example.com を開き、同じページ内の文字検索を5回行う専用依頼を使用する。実引数とツール名を確認した既知の閲覧・検索だけを試験ハーネスが許可する。単発5回とターン限定1回を比較し、次の依頼へ許可が継承されないこと、終了後の失効と適用件数、Gatewayの操作詳細表示・許可一覧を照合する。未知の操作は許可せず試験を失敗させる。タイムアウト時は専用依頼だけを停止する。常駐設定・既存会話・既存許可は変更しない。

### 初回実測

- GatewayのMCP・承認表示・配信回帰：34件成功（24 + 3 + 7）。実Discord操作を含まない。
- 常駐Proxy capability：`mcp_operation_details.enabled=true`、`mcp_turn_approval.enabled=true`、`native-item-id-v1`。
- 専用Response `resp_3309a192-1cc2-4f3f-be27-24a7191de20a` は実Codexでページ遷移1回・`browser_find` 5回を実行し終了。保存回答は取得できたが、interactionsは0件。したがって承認フロー試験は**未合格**。
- 呼出し履歴と読み込まれたCodex設定を照合すると、`browser_find` の `approval_mode="prompt"` が設定されていなかった。Proxyの機能有効化・対象一覧だけでは、上流Codexが確認不要として実行するツールに確認要求は発生しない。
- 承認フローを試すには、隔離した試験環境で対象ツールに上流の実行前確認を設定する。本番で常時許可するツールを、試験のために確認対象へ変更しない。利用者の判断により本番browser_findは常時許可を維持する。今回の承認なし実行は設定に整合した正常動作であり、Gateway不具合ではない。確認要求をGatewayが捏造したり、モデルの完了文だけで合格にしてはいけない。

### 利用者によるUI見直し指摘

操作詳細を別ボタンの先へ隠さず、最初に判断材料と単発／現在の依頼内の同ツール許可／拒否を示す方向を検討する。現行0.3は実引数をrequester_onlyとするため、単に公開カードへ転記しない。公開可能な説明と秘密情報の扱いをProxyと整合させ、文書・実装・実Discordの受入を更新するまで、現行の二段階UIが是正済みとは扱わない。

## 2026-09-17 インライン0.4：実Proxyとの接続試験

常駐Proxyと同じ配備バイナリを、別ポート・別DB・別Codex homeで起動して検証。本番設定は変更せず、隔離環境だけbrowser_findをpromptにした。実Codex／実MCPを使い、Discord HTTPは試験用transport。実利用者のDiscord表示・押下確認とは区別する。

- `resp_5c3c2ce7-ca2c-463d-95e2-aa094aa2f02b`：新しいインラインカードの公開対象を照合して依頼中許可。検索5回に確認1回、application_count=5、終了時expired。
- 同じ会話の次Response `resp_c2e4732e-c03c-44c0-b58e-b344a02bf173`：新カードから単発許可を5回。検索5回に確認5回、許可一覧は空。前依頼の許可継承なし。
- once-turn試験は132.63秒で合格。IDは隔離環境の記録であり、本番API照会用ではない。
- 試験ランチャーのdisabled providerに必須codex_idを補い、起動失敗時の診断を追加。最初の結合試験で試験用Discordのエラー通知経路が404だったため補完し、画面配信のDB確定を待って押す方式と許可記録の事後照合を追加した。修正後に新規IDで上記試験を完走した。

常駐Proxyへの読取確認ではreadyと3 capability（details/turn/inline）が有効で、inline profileはsource-conversation-v1。実DiscordのIN-08は、本人による実表示・押下・結果確認が残る。


取消試験のハーネス修正：インラインカードには単発とターンの2つの許可ボタンがあるため、処理済み管理はcustom_idではなくinteraction単位にした。取消直後に、表示更新待ちの同じカードの単発ボタンを新しい要求として拾っていた。終了済みoperationではargumentsがnullとなり、旧ハーネスは「unexpected search」で中止していた。未知の実操作を許可したものではない。配信確定待ち・本人限定エラー応答の受け口・許可意思のDB記録照合とともに、実試験の誤判定を修正した。


取消試験の最終結果：`resp_bc494065-2ae6-4a3d-ac95-c7528d07e865` で新カードから依頼中許可し、Gatewayの一覧・取消経路でoperator_revokedを確認。その後4回の単発確認を経て計5回の検索が完了し、適用件数と確認件数も一致した。117.41秒で合格。ログ上、取消後の4回中3回はインライン、1回は本人限定詳細経路だった。その補足理由は本試験ログに保存していないため、全呼出しが公開カードで完結したとは報告しない。全5回がインラインで完結した単発試験は前述once-turnの次Responseで確認済み。実Discord表示の受入時にも例外表示を確認する。
