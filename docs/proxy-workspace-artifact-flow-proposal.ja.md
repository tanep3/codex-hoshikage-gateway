# ワーク管理と再取得可能な成果物の調整案

版: 0.3（製品向けの責務・復旧契約案）
日付: 2026-09-11
宛先: Proxy担当「Codexプロバイダのバグ修正」
状態: **Gateway側の推奨案。Proxyからの追加提案を取り込み、下記の具体契約への回答を依頼する。双方の契約確定・実装完了・実機検証完了を意味しない。**

## 1. 今回の回答と前案からの変更

Proxy提案の5点に賛成する。実装量の削減を理由に、成果物の再取得や通常操作の使いやすさを削らない。Gatewayにcwd設定やProject登録を要求せず、会話を始め、作業を依頼し、成果物を選んで受け取り、配信障害後も同じ成果物を受け取れる構成を採用したい。

本案は前案の「全会話で共有ワークを既定とする」「取得時の一時コピーを返すだけ」の提案を置換する。過去の共有ワーク案を合意済みの製品仕様として残さない。

| 項目 | 今回の推奨 |
| --- | --- |
| 新規会話のワーク | Proxyが自動割当。共有は明示選択した場合だけ |
| 継続 | Proxyが保存済みの会話・ワーク対応を継承 |
| 成果物 | Proxyが不変の保存コピーとartifact_idを管理 |
| 通常の取得 | 登録済み成果物一覧から選択。相対パス指定も残す |
| 再配信 | 同じartifact_idから再取得。AIを再実行しない |
| 実行中・失敗・中断 | 実行状態だけで取得を禁止しない |
| Gatewayのtemp | 配信用キャッシュ。原本・成果物正本・実行先ではない |
| 運用設定 | 安全な標準値を同梱し、一般利用者に容量計算を要求しない |

既存Gateway要件・設計には共有ワーク・全体1実行など移行途中の記載がある。それらは本案に対する確定仕様ではない。契約合意後に一括更新し、異なる前提のまま実装を再開しない。

## 2. 利用者から見た標準フロー

1. 許可されたサーバーでBotへ話しかける。全投稿／メンション時のみの応答設定に従う。cwdやProjectの登録は不要。
2. 通常チャンネルはその会話、フォーラムは投稿ごとの会話として継続する。既定モデルを使い、変更時だけモデルを選ぶ。
3. 「PDFを作って」と依頼する。対応する成果物登録経路でProxyに登録されたファイルは、Gatewayで選べるようになる。
4. `/get` でファイル名・サイズ・作成日時・期限が分かる一覧を開き、受け取りたい成果物を選ぶ。内部IDを覚える必要はない。同名の異なる版を見分けられる表示にする。
5. 未登録のファイルは `/get path:output/report.pdf` で保存版を作って取得できる。「同じ版を再送」と「現在のファイルから新しい版を取得」は別操作として案内する。
6. 配信失敗後は同じ成果物の「再送」を選べる。既に保存された内容は原本の更新やGateway再起動で変わらない。期限切れならその事実と、原本から新しい版を取得できるかを案内する。

一覧を表示することとファイル本体の配信許可は別に扱う。利用者の選択または対象が確定した明示的な返送依頼をGatewayが記録し、配信を開始する。「作って」だけで無条件にファイルを送り付けず、回答本文中のパスを送信指示と見なさない。通常の成功時に依頼IDや内部状態を並べず、操作が必要な場合に短く理由と次の操作を示す。

## 3. 責務境界

| 領域 | Proxy | Gateway |
| --- | --- | --- |
| 会話・実行先 | 汎用の会話IDとworkspace_id、作成・選択・継承・権限検証 | Discordの会話場所とProxyの会話を対応付ける |
| 実行 | App Server所有、実行先制限、実行記録、ワークの競合制御 | Discord受付、キュー、全体実行上限、承認・Steer・中断操作 |
| 成果物 | 安全な読取り、保存コピー、登録・一覧・照会・取得、期限・容量・ハッシュ | 選択UI、Discord上の認可、受信検証、添付配信 |
| 復旧 | 作成要求とartifact_idの永続対応、保存物の照会・再取得 | 配信待ち・送信試行・結果不明・送信先の永続管理 |
| 一時領域 | コピー作成中の領域と成果物保存領域の管理 | 私有tempの配信用キャッシュ、回収 |
| 認可 | 認証主体、ワーク操作、成果物取得の権限を毎回検証 | 本人・Guild・チャンネル・会話・配信先を毎回検証 |
| 制限・案内 | Capability、機械可読エラー、有効な制限・期限 | Discord側の制限と合わせ、利用者に対処を案内 |

同一ホストでも別ホストでも認証付きHTTPで本体を伝送する。GatewayはProxyのローカルファイルを開かず、絶対cwdを取得・保持・送信しない。Discord ID、Bot token、Discord送信処理をProxyへ持ち込まない。GatewayからProxyの許可ルート・sandbox・サービスを変更しない。

現行の[Control API契約](../../codex-hoshikage-proxy/docs/control-api.ja.md)は共有認証主体であり、汎用ファイル転送と最終回答再取得を提供していない。本案の機能を現在実装済みと扱わず、ワーク・成果物管理を汎用APIとして追加する契約改定を依頼する。

## 4. ワークの自動割当と継承

### 4.1 自動割当

Proxyが管理するルート以下に、汎用の会話識別子に対応したワークを作成する。利用者が会話ごとにディレクトリを用意したり、Gatewayへ許可ルートを設定したりする必要はない。Proxy運用者が管理ルート・容量を管理する。

Gatewayは会話作成用の安定した不透明キーを送れるものとする。Discord IDそのものは送らない。同じ作成要求への再照会・再試行でワークや会話が増えない契約が必要。初回Turnの開始失敗とワーク作成成功を区別し、Responseが成功していないだけで作成済みワークを取り違えない。

会話作成を独立APIにするか、新規Responses要求に統合するかはProxyが提案する。どちらでも開始応答の喪失・再起動後に対応を照会できること、実行を再送せずに解決できることを必須にする。

### 4.2 継続・共有・競合

- 継続は保存済みのworkspace_idと実体を使う。既定ルート変更・再起動で既存会話を移さない。権限と実体の同一性を再検証し、不明・撤回時は推測で継続しない。
- 共有はProxyに登録済みのワークを表示名で明示選択する方式を提案する。Gatewayへcwdを入力させない。通常の自動割当と同じAPI・認可経路を使う。
- 共有を選ぶ際は、同名上書き・相互閲覧・共同作業になることをGatewayが示す。既存会話の実行先を黙って切り替えず、原則として新規会話の開始時に選ぶ。
- Gatewayの全体2並列という既決定を基本に戻し、異なる自動割当ワークは並列化可能にする。同一会話は同時1実行。共有ワークや包含する既存ワークの競合はProxyが他クライアントも含めて制御し、Gatewayのローカルな排他だけで保護済みとしない。
- Approval・Interrupt・Steer・状態照会は新規Turn実行枠の外で処理する。成果物コピーにも別の容量・処理上限を設け、コピー負荷でControl Planeを塞がない。

ディレクトリを分けることは、別利用者間のセキュリティ隔離を意味しない。現在の本人専用・共有管理主体の範囲を維持する。Proxyは実行sandboxと取得APIの実際の境界を明記し、実装していないマルチテナント隔離を主張しない。通常の会話別一覧は会話に関連付けられた成果物を返し、共有ワーク全体の一覧は明示的な別範囲として扱う。

### 4.3 データ寿命

ワーク原本の寿命と保存成果物の期限は別である。会話リセット、Discordのチャンネル削除、成果物期限切れを理由にワーク原本を自動削除しない。容量不足は明示し、管理操作で対象と影響を確認して整理する。workspace_idやartifact_idを削除後に再利用しない。

## 5. 成果物の作成・登録・一覧

### 5.1 保存版の作成

成果物作成要求は、会話／実行の識別子、ワーク内の相対パス、安定した作成要求IDを受け取る。任意の絶対パス取得APIにしない。Proxyは実行先・現在の権限・ファイル種類を検証し、安全に開いた同一fdから容量制限付きでコピーし、永続化したバイト列とメタデータを公開する。

公開する成果物には少なくとも `artifact_id`、会話・workspaceとの関連、分かる場合のResponse/Turn、表示ファイル名、実サイズ、メディア型、SHA-256、作成時刻、期限、状態を含める。実行に関連することと、その実行が原本を生成したという証明は区別する。絶対パスや秘密を表示情報へ含めない。IDを知っているだけで取得できる公開URLにはしない。

同一作成要求ID・同一内容の要求は同じ作成処理／artifact_idを返し、異なる内容なら競合エラーにする。応答が途切れたら要求IDで照会し、原本が変わった新しいコピーを同じ操作の結果にすり替えない。コピー途中のクラッシュで内容を確定できない場合は失敗／不明として照会可能にし、黙って再コピーしない。新しい版の作成は新しい操作IDで行う。

### 5.2 「登録済み一覧」を成立させる経路

一覧APIだけでは通常の利用手順は成立しない。次の登録経路を製品機能として契約化する。

- モデル／実行側が相対パスと表示情報を構造化して提出し、Proxyが検証・保存コピーを作成する汎用の成果物登録機能。ツール等の具体的な公開方法、利用モデルへの提供方法はProxy側から提案してほしい。
- Gatewayの `/get path:...` による利用者指定も同じ登録処理を使う。
- 登録完了後にだけ「受け取れる成果物」として一覧へ掲載する。原本のパスを登録しただけで保存済みと表示しない。
- 一覧はページングでき、再起動・通知欠落後も会話から再取得できる。通知は一覧の正本にはしない。

回答文の解析、Git diff、作業フォルダーの無差別探索を成果物登録の根拠にしない。登録はファイルの配信許可でもない。モデルが登録したファイルもGatewayが利用者の配信操作に結び付けて送る。登録経路を提供できない場合は「通常は一覧から選べる」を実装済みとせず、契約確定前の不足として扱う。

### 5.3 実行中の取得と整合性

実行中・失敗・中断でも、対応するワークと権限を確定でき、対象ファイルを安全に読めれば作成を許可する。開始前拒否などで実行記録がない場合でも、有効な会話・ワークの記録を根拠にできるかを契約で定義する。成功Responseだけを取得の唯一の根拠にしない。

symlink、特殊ファイル、範囲外への脱出、パス差し替えを防ぎ、読出し中に変更を検出したら「更新中」としてコピーを公開しない。メタデータ比較だけではすべての同時変更を検出できない。**READYになった保存コピーの内容が不変である保証と、原本が単一時点で整合していた保証は別**とする。完成を明示して登録する経路を通常手順とし、任意に書換え可能な原本の原子的snapshotは保証しない。

## 6. 成果物ストアとHTTP契約

以下は必要な操作の意味であり、endpoint名やフィールド名の最終指定ではない。Proxy側で既存APIとの整合を取った契約案を返してほしい。

| 操作 | 必須の結果・性質 |
| --- | --- |
| 会話／ワーク作成・照会 | 要求IDによる重複排除、保存済み対応の復元、共有選択の権限検証 |
| 成果物作成・要求照会 | 上記の作成要求ID、進行状態、確定したartifact_id、競合・不明の区別 |
| 会話の成果物一覧 | ページング、版を識別するメタデータ、状態・期限、認可された範囲 |
| 成果物情報・本体取得 | 同じIDは同じバイト列、長さ・ハッシュ、認可、期限・失効・破損の区別 |
| 保持予約・延長・解放 | 配信待ち中の有限な保持期限を返す。上限・拒否理由・重複処理を定義 |
| Capability・制限照会 | 契約バージョン、対応機能、有効サイズ・保存容量・保持上限・処理制限 |

成果物状態は少なくとも作成中／取得可能／作成失敗／結果不明／期限切れ／権限失効／破損を区別する。公開前に本体とメタデータの整合した永続化を行い、再起動時は途中ファイル・孤立記録を検査する。READYなのに本体がない場合を別の原本からの再作成で隠さない。

機械可読エラーは、未存在、対象不一致、権限不足、更新中、サイズ超過、保存容量不足、処理上限、期限切れ、破損、契約不一致、状態不明を区別し、再試行可能性と必要なら待機時間を返す。Gatewayは秘密を含む生エラーをDiscordへ転送しない。

保持期間内はディスク逼迫を理由に保存済み成果物を黙って追い出さない。容量を予約して新規作成を制限し、期限切れの回収や管理操作と区別する。作成要求の重複排除記録は本体期限切れ後も同じIDを新しい版として再利用させない期間・削除規則が必要。原本や実行記録の保存寿命と混同しない。

Proxyの成果物保存領域も管理対象のデータである。バックアップは実行記録・成果物メタデータ・本体の整合を扱い、巻戻しや欠損を検出する世代情報を契約化する。Gatewayの古いDB復元で別の成果物や別Proxyインスタンスへ結び付けない。

## 7. Gatewayの配信復旧

Gateway DBには作成操作ID、artifact_id、Proxyのインスタンス識別、会話、配信先、版の検証情報、期限／保持予約、配信状態、DiscordメッセージIDを保存する。ファイル本体はDBに入れず、`~/.config/codex-hoshikage-gateway/temp` を既定とする私有キャッシュへ受信する。利用者にその場所の登録を要求しない。

受信は実バイト数を制限し、サイズ・ハッシュを照合してからDiscordへ渡す。Proxyのファイル名をローカル保存パスとして使用しない。再起動後にキャッシュが消えても、保持期間内なら同じartifact_idで再取得できる。

- 配信開始前に有限の保持予約を取得し、期限をDBへ保存する。GCと取得の競合をProxyが制御する。
- 配信確認後はGatewayキャッシュを削除し、保持予約を解放する。これはProxy成果物の即時削除指示ではない。元の期限まで通常の再取得を可能にする。
- 保持延長にはProxy側の上限を設ける。Gateway長期停止や無期限の障害で永遠に容量を占有しない。延長不可・期限切れは配信状態に反映する。
- Discordへの送信前後を永続管理する。送信失敗が確定した場合と、応答喪失で送信結果が不明な場合を分ける。
- 結果不明なら既存メッセージとの照合で解決し、自動的な別投稿で重複を隠さない。解決できない場合は利用者に不明を示して明示再送を受け付ける。
- 配信再開時も本人・Guild・チャンネルの認可を再検証する。別ホストへのGateway移行は同じDBとProxy対応を復元する管理手順で行い、キャッシュの共有を必要条件にしない。

Codex実行、成果物作成、ファイル取得、Discord配信は独立した状態として扱う。いずれの復旧でもCodexを自動再実行しない。

## 8. 制限と製品の既定値

Proxyの保存容量・コピー中の一時容量・同時処理・保持期間と、Gatewayのキャッシュ・Discordへの送信条件を別々に管理する。有効な返送上限は双方の制限から算出し、一覧・選択時点で返送可否を案内する。Discordへ送れないサイズだからといって、Proxyの成果物を破棄しない。

標準値は実装担当が対象環境で測定し、根拠とともに設定例・既定値・運用資料へ揃える。一般利用者に全項目の入力を要求しない。以前の「25 MiB・同時2件」は成果物処理の確定値として採用しない。新規Turn全体2並列という既決定とは別の制限である。

期限を見える形で提示し、無期限保存と誤認させない。導入時と再接続時にCapability・有効な制限を検証する。対応不足時に共有ワークや不安定なファイル直読へ黙って切り替えない。旧Proxy向け互換モードを残すなら、利用者に機能制限が分かる明示モードにし、製品標準の受入完了とは区別する。

## 9. 移行と関連する復旧の不足

旧会話は保存済み実行先を確実に特定できる場合に限り、元のワークを既存ワークとして引き継ぐ。自動割当先へ無断で移動しない。特定不能な場合は理由と新規会話の操作を案内し、旧履歴・原本・要求記録は削除しない。旧送信待ちを異なるワークで自動実行しない。設定変更・ビルド・再起動は検証後に一つの移行手順にまとめる。

成果物再取得を実装しても、現行Proxyが最終回答テキストを再取得できない問題は解決しない。製品としての回答配信復旧も必要なため、**Proxyが確定した最終回答を有限期間保存し、Response IDから認証付きで再取得する契約**を関連提案とする。Gateway DBへ本文を重複保存しない既定方針を保ち、回答保存の機密性・容量・保持・削除を成果物とは区別して定義したい。全ツール出力やSSE全履歴の保存を必須にする提案ではない。

これは現在の「最終回答再取得なし」契約を変更するため、Proxy側から対応案を明示してほしい。採否を未回答のまま「再起動しても回答を届けられる」と宣伝しない。成果物保存による復旧と文章の復旧を別々に受入確認する。

## 11. 合意と受入の条件

順序は **本案へのProxy回答 → API契約とGateway要件・設計の一括確定 → 両側実装 → 結合・障害試験 → 導入案内** とする。方針だけの同意やMock成功を製品の完成判定にしない。

| 試験 | 確認する結果 |
| --- | --- |
| 未登録の通常チャンネル・フォーラムで会話 | cwd登録・モデル再入力を強制せず、意図した単位で履歴とワークを保持 |
| 初回開始失敗、作成応答喪失、Proxy再起動 | ワークと成果物を重複作成せず、要求IDで結果を照会 |
| 別会話で同名ファイルを作成 | 自動割当では上書きしない。明示共有では共有範囲を表示 |
| 既定値変更・旧会話継続 | 元の実行先を維持。不明な旧記録を推測移行しない |
| モデルによる登録、利用者によるパス指定 | どちらも不変の成果物となり、再接続後も一覧から選べる |
| 原本更新・削除後、同じIDで再取得 | 元の保存版と同じサイズ・ハッシュ・内容 |
| 実行中・失敗・中断した作業の取得 | 安全に読める対象は取得でき、検出した更新中は成功扱いしない |
| 差し替え・symlink・特殊ファイル・権限撤回 | 範囲外取得や保存版による権限迂回を防ぐ |
| Gateway再起動・temp消失・別ホスト | DBの同じartifact_idから再取得し、元の配信先へ認可付きで復旧 |
| Discord送信成功後の応答喪失 | 結果不明を区別し、自動の重複投稿・AI再実行をしない |
| 期限境界・GC・容量不足・長期停止 | 保持契約を破らず、有限な期限と対処を利用者へ案内 |
| バックアップ復元・保存物欠損 | ID取り違え・黙った再生成を防ぎ、破損／復元隔離を検出 |
| 全体実行枠・コピー枠の飽和 | 承認・中断・Steer・状態確認が実行枠待ちで止まらない |
| 回答テキストの配信失敗・再起動 | P-O01の契約に従って同じ確定回答を回収。成果物の試験で代用しない |

試験環境・機密データの扱い・保持値を双方で確定し、別ホスト構成も含む実環境で確認する。現行のコード・インストール・設定・稼働DB・Proxyサービスは、本書の調整だけでは変更しない。
