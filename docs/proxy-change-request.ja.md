# Proxyへの追加要件と責務境界

更新日: 2026-09-11

## 依頼の位置づけ

既存のProxy改定依頼と、その精査結果を踏まえた追加依頼。本書はGateway側からのAPI契約案であり、Proxy担当による実現性確認・契約回答を求める。Gatewayはこれから実装する。

著作者は必要なProxy拡張と両プロジェクト間の要件調整を許可している。ただし未確定の利用方法を勝手に確定しない。既存作業とユーザー変更を尊重し、この文書だけを根拠に常駐サービスの再起動や権限変更を行わない。

**連携状況:** Proxy担当の`docs/control-api.ja.md`による契約回答を確認済み。2026-09-11に常駐Proxyの認証付きGETで`/readyz=ready`と制御API契約1.0のCapabilityを確認した。以下は依頼履歴として残し、現在の契約・Gateway側の対応は要件定義書の第3章・D-01を参照する。

**出力保存の解釈:** Proxy文書の「Gatewayが受信済み出力を保存」は、本Gatewayでは配信処理中のメモリ保持とDiscordへの配信で対応する。DBへの回答の重複永続保存は行わない。再起動で失った未配信部分は取得不能と表示し、生成を再実行しない。この対応にProxy側の実装・文書の追加変更は要求しない。

## 最新の確定事項

- GatewayはRust、永続化はSQLite。本人専用、Project＝Discord Channel、Conversation＝Discord Thread。
- 初版に会話、承認、中断、Steer、モデル選択、添付、未送信依頼の自動復旧を含める。全体の実行並列数は2。
- 以前の依頼の「Steerを追加しない」は撤回された。**汎用的なTurn Steer APIが必要。**
- **同じ会話の文脈を保ったモデル変更は初版必須。P-09を実装対象とする。** 添付は画像・UTF-8テキスト入力と成果物返送。Discord添付の取得・復旧・送信はGatewayが担当する。
- Proxyは汎用Proxyとして維持する。GatewayはApp Serverに直接接続しない。

## 責務の境界

| 対象 | Gateway | Proxy |
| --- | --- | --- |
| 利用者 | Discord利用者・サーバー・チャンネルの認可 | APIクライアント認証、操作対象のアクセス範囲の検証 |
| 会話 | Discordと会話の対応、開始操作 | 汎用のResponse／Thread／Turn対応、上流の会話開始・継続 |
| 依頼 | Discord重複イベント排除、待ち行列、並列枠、取消・再開UI | 汎用要求IDによる受付記録、上流実行・状態照会、同一Threadの競合拒否 |
| 承認 | 判断者の認可、ボタン、内容表示 | 一意な承認ID、期限・判断状態、上流への回答、実行権限制約 |
| Steer・中断 | 操作UI、対象の選択、停止後の待ち行列制御 | 対象Turnの照合、上流への制御要求、受付結果と実状態の提供 |
| 表示・復旧 | Discordの分割・更新・送信失敗管理、未送信の本文・添付復旧 | 状態の観測時刻、実行との対応保存、取得可能な出力・承認状態の提供 |
| モデル | 選択UIと既定値、適用単位の管理 | モデル一覧、能力検証、指定モデルの上流への反映とエラー |
| 添付 | Discordからの取得・サイズ制限・一時保存・成果物アップロード | 対応済み入力の上流転送。追加の汎用機能は不足が確定してから協議 |
| 運用 | Botの接続・復旧、Gateway独自のSQLite | 上流接続、Provider容量制限、Proxy自身の障害復旧 |

ProxyへDiscord ID・Botトークン・Discordの待ち行列・スレッド作成・表示・送信ルールを持ち込まない。Gatewayの並列数2はProxy全体の上限変更を意味しない。Proxy側の永続化方式は既存設計に合わせてよく、GatewayのSQLite採用に合わせる必要はない。

## Proxyに求める契約

### P-01: 実行の識別と送信結果の照会

Responses開始時にResponse ID、Thread ID、Turn IDをクライアントが取得できる契約を定める。上流開始前はTurn IDが未確定でよいが、その状態を明示する。

Gateway生成の汎用`client_request_id`等で、ID応答を取り逃しても受付状況を照会できることを提案する。Proxyは上流送信前に受付・送信境界を永続化し、上流送信後にクラッシュして結果を特定できなければ`unknown`とする。分散処理全体のexactly-once完了を保証したとは扱わない。

同一クライアント・同一要求IDの重複要求で別Turnを開始しない。同一IDで内容が異なる要求は競合として拒否する。保持期限を過ぎたIDやストア障害時の扱いを明記し、根拠なく「未送信」と判定しない。Gatewayは送信結果不明な要求を自動再送せず、照会に使う。

### P-02: 明示的な中断

対象TurnからThreadを解決して`turn/interrupt`を呼ぶ汎用APIを提供する。要求受付と中断完了を区別し、不存在・終端済み・重複・完了との競合の結果を定義する。実行枠を待つ新規依頼と同じ待ち行列で中断を詰まらせない。

中断は変更の巻き戻しではない。子プロセス・バックグラウンド処理をどこまで止められるかを報告し、確認できない停止を成功扱いしない。Gateway側の待機依頼を停止・削除する機能はProxyには不要。

### P-03: Steer（追加必須）

汎用のTurn制御APIとして実行中Turnへ入力を追加する。`expectedTurnId`相当の対象照合を必須とし、別のTurnが始まった場合に誤って注入しない。

- Steerは新しいTurn開始でも中断でもない。受付がAIの指示遵守や停止の保証でないことを明記する。
- 実行中Turnなし、対象不一致、承認待ち、中断要求中、終端との競合を定義する。
- Steerにモデル・cwd・sandboxの変更を混在させない。
- 制御要求IDを使う場合は重複・結果不明の契約を定義する。結果不明なSteerを自動再送しない。
- 通常の同一Thread競合拒否は新規Turn開始に適用し、実行中Turnへの正当なSteer・承認・中断は通す。

### P-04: 実行記録と会話継続

Response／Thread／Turn／モデル／最後の状態／観測時刻を永続化する。再起動後の現在照会結果と、保存済みの最終観測を区別する。上流照会不能は`unknown`相当として返し、自動実行しない。

実行記録と`previous_response_id`として継続可能かは別の情報とする。初回中断、途中失敗、実行中、結果不明、完了後の継続条件を定める。旧データ形式と既存の成功会話継続を維持する。

### P-05: 承認の安全性

先方レビューで指摘された再起動による承認ID再利用を解消する。古い承認が別操作へ作用しない、一意なIDと対象照合を提供する。

期限切れ・拒否・キャンセル・重複判断・再起動後の無効化を定義する。Codex側に回答経路が残っていない承認をUI上だけ復元可能としない。再接続時に現在有効な未処理承認を照会できること。

Thread単位で承認コンテキストを上書きして別要求と混ざることを防ぐ。上流通知にTurn IDがない場合も、競合拒否や実行世代との関連づけにより誤適用を防止する。

### P-06: 切断・再接続・出力

現在のResponses切断時中断の意味を黙って変更しない。GatewayがResponsesを完了まで維持する方式を基本案とする。Gateway再起動をまたぐ実行継続を既定にする要求は出していない。

Turnイベント監視の接続・再接続時に状態と有効承認を再取得でき、イベントの重複・欠落を識別できる契約を提案する。全イベント永久保存は要求しない。

最終回答を取り逃した場合に、Proxyから再取得できるか、上流から再構成できるか、取得不能とするかを明示して回答する。出力保存を追加するなら保持期間・サイズ上限は協議事項。出力の取り逃しを理由に実行を再送しない。

### P-07: Capabilityと互換性

契約バージョンに加え、開始時ID、要求ID照会、状態永続化、中断、Steer、対話承認、自動承認抑制、イベント再接続、出力再取得の対応状況と制限を機械判定できるようにする案。稼働状態の`readyz`とは分ける。実装していない機能を利用可能と返さない。

既存Responses、Chat Completions、モデル一覧、OpenWebUI経路、各Provider、認証、承認の互換性を維持する。新規オプションを指定しないクライアントの意味を変えない。汎用APIとして命名し、DiscordやGateway専用の概念で公開APIを構成しない。

### P-08: 権限設定（調査・契約提案）

共有Proxyの権限上限を強制し、クライアント指定は制約を強める方向だけにする。ワークスペース自動承認を要求単位で抑制する案を精査する。上限がfalseの場合にクライアント指定でtrueへ昇格させない。自動承認を抑制しても全操作に承認が発生するわけではない。

クライアント／要求別にどこまで分離できるか、同じThreadの継続時に制約が緩まないかを回答する。Thread・Turn・承認の操作範囲も認証主体との関係を定義する。サーバー管理者の権限設定までGatewayに任せない。

現在の設定ファイルはworkspace-write、自動承認false、ネットワークfalse、許可cwdルートは`/home/tane/work/codex-hoshikage`。LAN用`0.0.0.0`待受はユーザーの意図なので維持。これらをGatewayのために一括変更しない。必要なプロジェクトルートは別途著作者と決める。

### P-09: 同じ会話のモデル変更（必須）と添付の境界

**同じ会話の文脈を保ったモデル変更を実装対象とする。採否の回答待ちではない。** モデル選択UIはGatewayが担当し、Proxyは上流へのモデル指定と会話継続を提供する。

継続時の`model_mismatch`制約を単に削除するだけでなく、保存モデル情報、次のTurnへの適用、旧Responseからの継続、変更失敗時の整合性、再起動後の復元を検証する。実行中Turnのモデルは変更せず、次のTurnから適用する。会話履歴を黙って破棄・要約置換しない。プロバイダを跨ぐ切替等で制約があれば、対応範囲と具体的なエラー契約を回答する。

添付は画像・UTF-8テキスト入力と成果物返送を採用。既存画像入力を再利用し、Discord添付の取得・テキスト取込み・Discordへの成果物アップロードはGateway側とする。Proxyへの一般ファイル配信・文書変換・アップロードAPIは現時点で要求しない。必要な汎用の不足だけを協議する。成果物はGateway側の`/get`による本人の明示指定で取得・返送し、自動探索・自動送信しない。Proxyの構造化成果物情報は必須にしない。

## 試験と完了報告

API契約案としてURL、認証、要求・応答例、エラー、状態遷移、保持条件、互換性を先に文書化する。要件が確定していない項目は調査結果と選択肢を返す。著作者への質問はGateway側でまとめられるよう明示する。

少なくとも、開始前後のクラッシュとID照会、重複要求、古い承認ID、同一Thread競合、Steer終了競合、中断完了競合、再接続時の承認、最終出力の取り逃し、旧保存データの読込、同じ会話のモデル変更後の文脈継続、モデル変更失敗時と再起動後の整合性を検証する。既存App Server異常終了→Proxy終了→systemd再起動は再実装ではなく回帰確認とする。

模擬上流との自動試験と、実Codexで確認できた範囲を分けて報告する。常駐サービスを落とす試験の影響範囲は事前に具体化する。

Proxy側の回答には、実装可能な汎用API、Gatewayに残す処理、未確定事項、既存利用者への影響、受入試験を含めてほしい。Gateway要件本文は同じサーバーの `/home/tane/dev/AI/codex-hoshikage-gateway/docs/requirements.ja.md` にある。
