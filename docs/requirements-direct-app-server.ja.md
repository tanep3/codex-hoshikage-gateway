# Gateway専属Codex App Server — 目標要件

版0.2 / 2026-09-18 / Tane Channel Technology

状態：目標構成の要件案。[構造転換の決定](architecture-direction-direct-app-server.ja.md)に基づく。現行サービスと[現行要件](requirements.ja.md)の動作を直ちに変更しない。移行手順と未確定の製品選択は本書末尾に残す。

## 目的と製品境界

Discord上の会話、作業依頼、承認、成果物受取を、一つのGateway製品として提供する。Gatewayが専属Codex App Serverを子プロセスとして起動し、stdioの双方向通信で操作する。稼働時にcodex-hoshikage-proxyのHTTP APIやサービスを必要としない。Proxyは別製品として残す。

**プロセス境界をなくしても内部の責務は分ける。** Discordの表示変更がCodex通信の解析を変えず、App Serverの通知変更がDiscord認可を変えないようにする。内部の境界はRustのモジュール、型、呼出し方向、保存上の正本で表す。汎用HTTP APIをGateway内に再構築することは目的ではない。

| DA-R06 | App Server送信前に送信意思と対象を保存する。送信結果不明のTurnや承認を新しいIDで自動再送しない。停止の受付と完了を区別する |

| DA-R08 | Codex認証、実行先、サンドボックス、ネットワーク、承認方針はGateway専属のCodex設定・運用権限で管理する。Discordから設定を勝手に拡張しない |

| DA-R18 | 全体2並列を維持し、各RunをGateway所有の専属App Server子プロセスで実行する。承認・停止はそのRunの子プロセスへ届け、他Runの設定や要求に流用しない |

## 内部責務の不変条件

- Codex transportはプロセスとプロトコルを所有し、利用者の権限やDiscordへの表示を決定しない。
- 実行管理は会話、依頼、Turn、作業先、モデル、排他、停止を所有し、Discord APIを直接呼ばない。
- 承認管理は上流の実call、表示証跡、明示判断、送信状態、失効を所有する。意味判定を後で追加してもCodex transportに埋め込まない。
- 保存管理は確定回答と不変成果物、保持期限、ハッシュ、取得状態を所有し、Discordへの送信先を決定しない。
- Discord層は本人確認、画面、配信を所有する。Codexや保存の結果を推測で成功に書き換えない。
- SQLiteの一つのレコードだけで「AI実行・回答保存・Discord配信」の三つを完了とみなさない。

| DA-A02 | Discordの別人／別会話の入力と古い承認が、実callや結果へ混ざらない |
| DA-A03 | 送信直前・送信直後・応答喪失・子プロセス異常終了・Gateway再起動で二重実行／二重承認を起こさず、UNKNOWNを保持できる |
| DA-A04 | App Server起点の承認・MCP入力と通常通知が並行しても、実call・引数・Turnの対応が維持される |
| DA-A05 | 最終回答・画像だけの回答・複数成果物・Discord送信失敗から、同じ保存版で復旧できる。期限切れや破損を成功表示しない |
| DA-A06 | 実行枠が満杯でも承認・拒否・停止・状態確認が進む |
| DA-A07 | 実Codexと実Discordで主要動線を確認し、模擬App Server成功だけを製品受入としない |
| DA-A08 | 旧Proxy経由の未終端依頼を、切替時に新しいCodex Turnとして自動開始しない。移行・保留・参照不可の状態を本人に説明できる |
| DA-A09 | 子プロセスは生存したままinitialize応答、Turn応答、承認返信応答、stdoutの読み取りが止まるケースを注入する。初期化時はreadyにせず、送信済みTurn／承認は到達を推測せず照会またはUNKNOWNで保護し、自動再実行・自動再許可しない |
| DA-A10 | Gatewayの正常終了・SIGKILL相当の異常終了・systemd再起動を隔離環境で試し、旧App ServerのPIDとその子孫が残らず、新旧の実行が重ならないことを確認する。回収を確認できない場合は新規受付を止める |
| DA-A11 | transport単体試験の直後に、同一App Serverの2並列Turnと別子プロセスからのthread再開を実証する。その結果を踏まえてRun別子プロセスを採用し、2並列RunのMCP設定、承認、停止、通知、モデル、出力の混線がないことを後続の結合試験で確認する |

## 未確定事項と推奨

1. **専属子プロセスの個数（決定済み）**：同時最大2つ、Runごとに専属子プロセスを所有する。単一子プロセスの2並列Turnと、別子プロセスからのthread再開は実機で確認した。ただし単一子プロセスにおけるMCP設定・承認方針の完全な隔離は未実証なので採用条件にしない。Run別構成の停止・承認・異常終了・復旧は引き続き受入試験を行う。
2. **既存会話の切替方針（確定）**：Discordの過去投稿と旧Gatewayの実行・配信記録は保持する。切替後の最初の発言から新しいCodex文脈を始める。旧Proxyのthread／response IDを新しいCodex子プロセスへ引き継がず、旧依頼を再送しない。切替直前の整合したバックアップを作成・検証し、未完了の依頼や配信があれば切替を拒否する。旧保存物の閲覧機能と保持期間は別途確定する。
3. **Codex専属設定の置き場**：設定ファイルの正本はGateway配下。認証情報とセッション保存先はファイル権限、旧Proxyとの同時利用、バックアップ範囲を確認して確定する。運用者の既存ログイン状態を黙ってコピーしない。
4. **画像・成果物の保存期間と容量**：現在の製品の利用実態とディスク容量から決める。Proxyの数値を根拠なくそのまま写さない。
5. **モデルの識別と互換表示**：既存の利用者向けモデル名を継続できるかをApp Serverからの情報で確認する。変更が必要なら利用者へ明示する。

本書は目標機能を定める。現在の設定例・導入手順は切替まで現行Proxy経由の運用説明として維持し、新方式の実装・受入後に英日双方を改定する。
