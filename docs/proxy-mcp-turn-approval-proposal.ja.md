# MCP操作の説明と作業ターン限定許可：Proxy調整案

2026-09-16 / 状態：双方の設計方針合意済み。具体API・上流対応付けの実証待ち。常駐環境の自動許可を有効にする合意ではない。

## 解決する問題

DiscordでMCPを利用すると、サーバー名とツール名だけの英語確認が繰り返され、利用者が具体的な操作を判断できない。直近のGateway記録では同一依頼に異なるinteractionが5件あり、各件がaccept→resolvedとなっていた。単なるイベント重複ではなく、個別の呼出し承認である。終了カードも5件残った。

利用者の希望は「今回のリプライターンに限り、同種の操作をまとめて許可」。次の依頼・別会話への許可の持越し、永続的な自動承認は求めていない。

## 利用者向け操作

- 「今回だけ許可」：現在表示している呼出し1件。
- 「この作業中、このツールを許可」：確認したMCPサーバー・ツールについて、現在のResponse/Turn内に限定する。ツールの引数が変わる呼出しも対象になることを説明する。単に「同種」と表記しない。
- 「拒否」：現在の要求を拒否する。
- 有効なターン限定許可の一覧と取消操作を提供する。取消は今後の呼出しへの許可を取り消すもので、実行済み操作は戻らない。進行中作業の停止は /stop。

同じツール名でも動作は同じとは限らない。特に browser_evaluate はJavaScript次第で読取り・変更・通信等が変わる。「閲覧だけ」と判断する根拠がない場合に、閲覧専用の許可と表示しない。対象サイトや読取り限定の制約を提示する場合は、Proxyが実際に強制可能な範囲に限る。

## Proxyに具体化を依頼する契約

### 1. 操作内容と同一性の構造化

既存interactionに紐づく、信頼できる上流情報から次を提供する。

- interaction・Response・Turn・会話・workspace・instance・復元世代の対応。
- MCPサーバーの安定した識別子と設定世代、ツール名、呼出しID。
- 確認対象の引数・URL・実行コード等、説明用の情報。秘密値は公開表示しないため、伏せる項目と確認できない範囲を機械可読にする。
- 操作説明の取得可否と不足理由。目的の要約がモデル生成の場合は、実際の引数とは区別する。
- 適用可能な許可範囲、範囲のfingerprint、説明のrevision。ツール単位許可で引数の変更も含むかを明示する。

英語文面からツール名を正規表現で抜き出した値や、空フォームという事実だけを、自動許可の根拠にしない。上流から取得できない情報を推測で補わない。実際のApp Server要求に情報がなければ、その不足と対応可能な取得経路をProxy側で確認する。

### 2. ターン限定許可の管理と適用

Proxyが汎用的な許可レコードの作成・照会・取消・失効・呼出しへの適用を管理し、GatewayはDiscordでの本人確認、表示、選択を担う。Discord IDやBot UIをProxyへ持ち込まない。

- 新規許可は利用者の明示選択時のみ。現在pendingのinteractionと表示revision・範囲fingerprintを照合する。
- 対象は厳密に同一のResponse/Turn、MCPサーバー設定世代、ツール識別子、許可された範囲。別ツール、別サーバー、別Turnへ拡張しない。
- 対象は実行前のMCPツール呼出し承認のみ。ツール内部の入力フォーム、認証URL、権限追加、秘密入力、破壊操作の別確認には流用しない。
- 作業完了・失敗・中断・/stop・許可取消・期限切れ・設定変更・復元世代変更で失効する。無期限に残さない。Steerの追加発言では既存許可を失効させ、依頼内容の世代を進める。失効受付後にSteerを送る順序と競合をProxyで保証する。承認ボタンは追加発言に含めない。
- Proxy再起動時は失効し、次の要求に持ち越さない。Gateway再起動時はProxyの同一Turn・有効許可を照会して表示を復元し、照会不能なら新しい許可を作らない。
- 作成・取消は永続Idempotency-Keyで照合できるようにする。受付・適用・取消と停止の競合順を定義する。通信切断時はGET照合し、別キーで許可を再送しない。
- 許可レコード作成と現在の呼出しへの回答の結果をそれぞれ照会可能にする。現在の回答が結果不明なら、後続への許可適用を保留する。
- どの許可がどの呼出しへ適用されたか監査可能にする。生の秘密引数を監査ログへ保存しない。

APIパスやフィールド名は未確定。既存のscope:sessionや包括許可への変換で代用しない。Capabilityで対応・範囲・期限を公開し、旧Proxyでは今回だけの許可を維持する。

### 3. 説明・適用の上限

説明・引数の上限、許可TTL、照会保持期間を具体化する。確認に必要な情報が上限で欠けたときは、その事実を表示し、範囲を理解できないままターン限定許可を出さない。

## Gateway側の表示と永続化

現在の英語確認を転記するだけの表示から、操作・対象・実際の引数と許可範囲を確認できる日本語カードへ変更する。Proxyの事実とGatewayの翻訳・要約を区別する。

許可ID・対象Turn・範囲fingerprint・状態・適用件数を記録する。自動適用のたびに新しい公開カードを作らず、同じ作業の許可カードの件数を更新する。正常終了時は不要な確認本文・終了文の連投を避け、許可範囲と終了状態を1枚へまとめる。失敗・結果不明の記録は正常終了として消さない。既存投稿の所有確認と送信結果照合を維持する。

Proxy照会結果が resolved であるだけでは「利用者が許可した」「ツール成功」と表示しない。許可操作と実行結果の証拠を分ける。

## 受入条件

1. 同一Turnで同じツールが5回呼ばれる場合、今回だけを選べば個別確認、ターン限定を選べば許可範囲に一致する後続4回のクリック不要。
2. 対象引数が変わる場合、許可範囲内かをProxyが判定する。別ツール・別サーバー設定・別Turn・範囲外は新たに確認する。
3. browser_evaluate の確認に実行対象・コード等が表示される。情報欠落時に推測した説明や閲覧限定という誤表示をしない。
4. ツール内部の別フォームやURL認証は自動回答しない。
5. 二重クリック・応答喪失・Gateway/Proxy再起動・停止/取消との競合・設定変更・正式復元で許可が拡大・復活しない。
6. 同じ承認の再配信と別呼出しを区別する。結果不明を自動承認・再実行で解消しない。
7. 実Codex・実MCPで説明→選択→反復呼出し→失効を確認する。次の依頼で再確認されることと、実Discordでカードが増殖しないことを確認する。

## 現時点の境界

現行interaction契約はMCPフォームへの個別acceptのみであり、信頼できる同種識別・操作引数表示・ターン限定許可の契約は未確定。Gatewayだけで英語文面を照合して自動acceptする実装は行わない。本提案に対するProxyの契約回答を受け、要件・設計・DB・テストを確定して双方を実装する。

## 追加合意

- browser_run_code_unsafe は常に個別確認。browser_evaluate は実引数・コード・権限の実証対象とし、評価未完了では個別確認を維持する。対象化が難しい場合も、操作表示と連続確認を減らす代替策を提示する。
- 本人・Discord会話・Gateway依頼IDを1 Agent Runの対応キーとして使い、ProxyのResponse/Turnおよび依頼内容世代に結び付ける。具体的なAPI識別子は契約回答で確定する。
