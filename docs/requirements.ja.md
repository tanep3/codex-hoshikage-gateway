## 3. 既存Proxyとの境界

2026-09-11にProxyの[汎用実行制御API v1](../../codex-hoshikage-proxy/docs/control-api.ja.md)を確認し、本書へ反映した。同日の常駐サービスへの認証付きGETでは、`/readyz`がHTTP 200・`ready`、`/v1/codex/capabilities`がHTTP 200・`contract_version=1.0`を返した。これは稼働中APIの読取確認であり、Gatewayからの実行・制御・再起動の結合試験ではない。

| 項目 | Proxyの契約・確認事項 | Gatewayの扱い |
| --- | --- | --- |
| 開始・識別 | Responses開始ヘッダーに`x-response-id`、`x-codex-thread-id`、`x-codex-turn-id` | IDを保存し、Responses接続を完了まで維持する。 |
| 重複防止・要求照会 | `Idempotency-Key`と要求ID照会。重複POSTは実行記録JSONを返し、新規実行しない | UUID由来の要求IDを送信前に保存。照会404は未送信の証明にしない。結果不明な要求を再POSTしない。 |
| 会話継続 | 成功Responseのみ継続可能。初回中断・失敗時は新規会話が必要 | 後続失敗では最後の成功Responseを利用する。初回失敗時は新規会話を案内し、黙って新規実行しない。 |
| モデル変更 | 同じProvider内で文脈を維持して変更。Provider間変更は409 | 同一会話の変更UIは対応範囲を表示し、次の依頼から反映。未対応の切替を成功扱いしない。 |
| 実行状態 | Turn照会に現在状態と最終観測・観測時刻。ID対応を永続化 | 保存状態と現在照会を区別し、実行確認不能ならUNKNOWN。 |
| 中断 | 明示Interrupt API。202は受付確認、終了は状態照会 | 停止ボタンは実行枠待ちに入れず、受付と停止完了を区別する。 |
| Steer | 明示Steer API。期待Turn ID必須。承認待ち・対象不一致等は409。Proxyの重複排除なし | Interaction ID等で送信開始を保存し、同じ操作を再送しない。結果不明を案内する。 |
| 承認 | UUID ID、対象照合、有効承認一覧、期限と上流書込状態 | 本人だけが判断でき、期待Thread/Turn IDを送信する。古いボタンを再利用しない。 |
| 自動承認抑制 | 要求でfalseを指定でき、Thread継続時も維持 | 対話承認と抑制を指定する。Proxyの権限上限は拡張しない。 |
| イベント | 接続時snapshotと欠落・リセット通知。履歴再配信なし | 再接続は状態・有効承認を再同期し、判断時に再検証。過去の回答deltaを復元できるとは扱わない。 |
| 回答再取得 | `output_retrieval=false`。最終回答・上流履歴の再構成APIなし | 回答はメモリに一時保持してDiscordへ配信する。DBへ永続保存せず、失った未配信部分は取得不能と表示する。 |
| 認証・分離 | 単一の共有管理主体。同じAPIキー間の所有者分離なし | 本人管理のProxyを利用。Botトークン・APIキーはDiscordへ渡さない。 |
| 添付 | 画像の既存入力経路のみ利用。汎用ファイル転送は追加しない | UTF-8検証・入力取込み・`/get`のファイル取得と返送はGatewayで行う。 |
| 追加質問 | user_input、MCP elicitation、権限専用承認は非対応 | 専用回答UIは初版対象外。待機検出・案内・中断経路は設計時に検証する。 |
| 障害復旧 | Responses切断は中断。Proxy/App Serverの異常復旧で要求を自動再実行しない | 未送信依頼だけ復旧。送信済みは照会し、切断しても上流実行が継続する前提にしない。 |

GatewayはDiscordの受付・認可・会話の対応づけ・待機制御・表示を担当し、Proxyは汎用実行・制御APIを担当する。この契約を技術設計の基準とする。実接続による受入試験と実運用パスの設定確認は別途行う。本確認では生成要求、承認・中断・Steer、サービス再起動、設定変更は行っていない。

## 5. 品質・安全性・運用方針

以下の推奨方針を採用する。数値、保存形式、APIへの対応方法は設計・検証で具体化する。

| ID | 方針 | 理由・検証観点 |
| --- | --- | --- |
| N-01 | 利用者許可リスト未設定・空の場合は受付を開始せず、設定不備を示す | 誤設定で全員に実行を許さない。Bot投稿やWebhook投稿の扱いも決める。 |
| N-02 | 許可サーバー・チャンネルを限定し、操作権限と閲覧権限を別に確認する | 操作できなくても会話や成果物を閲覧できる問題を防ぐ。DMは対象外とする。 |
| N-03 | 作業対象は明示登録とし、実際のパスはサーバー側で管理する | 過去の作業履歴や絶対パスを不用意にDiscordへ公開しない。 |
| N-04 | Gatewayの登録範囲とProxyの許可範囲を両方確認する | Gatewayへの登録だけでProxyの実行権限を拡大しない。 |
| N-05 | BotトークンをProxyへの要求・ログ・Codex入力に含めない | 不要な秘密の伝達を避ける。同一OSユーザーでの秘密ファイルの読取可否は別に確認する。 |
| N-06 | Discord操作時に毎回権限と対象会話を確認し、期限切れ・二重承認を受け付けない | 他人の操作や古いボタンが別依頼へ作用しないようにする。 |
| N-07 | Gateway専用のCodex会話を使い、同じ会話への依頼を直列化する | 他UIとの競合や応答の混在を避ける。全体2並列、同一作業フォルダーは1実行とする。 |

| N-12 | ログには診断用ID・状態・時刻を残し、本文や秘密は必要以上に保存しない | 保守性と情報管理を両立する。保存内容・期間・削除方法は未確定。 |

### 設計詳細

#### D-01: GatewayとProxyの操作経路

会話はResponses API、承認・中断・Steer・状態確認はProxyの制御API経由に統一し、GatewayはApp Serverを直接所有・起動・操作しない。

制御API契約1.0を使用する。主な経路は次のとおり。

| 目的 | API |
| --- | --- |
| 実行 | `POST /v1/responses`、`Idempotency-Key`ヘッダー |
| 要求照会 | `GET /v1/codex/requests/{client_request_id}` |
| Response記録と継続可否 | `GET /v1/codex/responses/{response_id}` |
| 状態照会 | `GET /v1/codex/turns/{turn_id}/status` |
| 中断 | `POST /v1/codex/turns/{turn_id}/interrupt` |
| Steer | `POST /v1/codex/turns/{turn_id}/steer`、`expected_turn_id`と`input` |
| 有効承認一覧 | `GET /v1/codex/turns/{turn_id}/approvals` |
| 承認取得・判断 | `GET /v1/codex/approvals/{id}`、`POST /v1/codex/approvals/{id}` |
| 監視 | `GET /v1/codex/turns/{turn_id}/events/stream` |
| 機能確認 | `GET /v1/codex/capabilities` |

必須の実行・識別・状態照会・承認・中断・Steer・同一Provider内モデル変更・自動承認抑制を起動時およびProxy接続の再確立時に再検証する。`output_retrieval=false`、snapshotのみの再接続、共有認証主体、成功Responseのみ継続可能という制約は対応済みの設計条件として扱い、それだけで起動拒否しない。Ready確認と機能確認を分ける。

新規Turn用の並列枠・待ち行列と、Approval／Interrupt／Steer／Status／Capabilityおよび復旧照会の処理経路を分離する。制御操作は新規TurnのSemaphoreや長時間保持される会話実行ロックを取得しない。認可・対象照合に必要な短い同期は許可する。HTTP接続・タスク処理も、実行中の長寿命ストリームだけで制御要求が塞がらないようにする。制御側の負荷上限は独立して設計する。

Proxy切断を検出した場合と再検証中は、Gatewayを新規依頼受付不可とし、待機依頼の新規送信も停止する。互換性・必須機能不足の場合は理由を表示して停止を維持する。既存Turnは利用可能で意味を確認できるAPIで監視・中断・承認・復旧を続け、使えない操作は成功表示せず案内する。再検証成功後も会話pauseとUNKNOWNによる保留は自動解除しない。

#### D-02: 会話と依頼の識別

以下の対応を永続化する。

| 対象 | 対応情報 |
| --- | --- |
| 会話 | DiscordサーバーID・プロジェクトChannel ID・Thread ID ⇄ Gateway会話ID ⇄ 継続用Response ID |
| 依頼 | Discord Message ID ⇄ Gateway依頼ID ⇄ Response ID・Turn ID（取得できた時点で記録） |
| 承認 | Proxy承認ID ⇄ Gateway依頼ID ⇄ Discord上の承認表示・判断者・期限 |

Discord Message IDを重複受付防止のキーにする。同じメッセージの編集で新しい依頼を暗黙に生成しない。編集・削除の扱いはD-04に従う。

送信前に送信開始状態を永続化し、同じ依頼の実行要求を再送しない。これはGateway側の送信回数の制御であり、Proxy側の冪等性や、操作が必ず一度完了する保証とは区別する。継続用Response IDを更新する条件は、失敗・中断・結果不明時も含めてAPI契約で定義する。

#### D-03: 依頼状態と復旧

| 状態 | 意味・主な遷移 |
| --- | --- |
| RECEIVED | 受付を永続化済み。認可・登録・容量確認後にQUEUEDへ。 |
| QUEUED | 未送信の待機中。実行枠取得後、送信前にSENDINGを永続化する。未送信の取消はCANCELLEDへ。 |
| SENDING | 送信開始境界を永続化済み。開始確認または現在照会で実行中を確認するとRUNNINGへ。終了確認なら対応する終端状態、判定不能ならUNKNOWNへ。 |
| RUNNING | Proxyで実行中と確認済み。承認待ち、完了、失敗、中断要求へ遷移。状態不明時はUNKNOWNへ。 |
| APPROVAL_REQUIRED | 承認待ち。判断後はProxyの確認結果に基づいて実行継続または終了状態へ進む。 |
| CANCEL_REQUESTED | 中断要求済み。停止確認が取れた場合だけCANCELLEDへ。完了と競合した場合は確認できた実状態を採用。確認不能ならUNKNOWNへ。 |
| COMPLETED | 完了確認済み。 |
| FAILED | 失敗を確認済み。失敗前の副作用がないことを意味しない。 |
| CANCELLED | 未送信での取消、または実行中断を確認済み。実行済み変更の巻き戻しを意味しない。 |
| UNKNOWN | 到達・実行・終了の状態を確定できない。自動再送・再実行の対象外。対象IDの一致する信頼できるProxyの現在照会で実行中ならRUNNINGへ、終了済みならCOMPLETED／FAILED／CANCELLEDへ訂正できる。UNKNOWNだった履歴は保持し、推測では訂正しない。 |

再起動時の復旧規則:

| 復旧対象・照会結果 | 処理 |
| --- | --- |
| GatewayのRECEIVED／QUEUED | 送信境界未通過をローカル記録で確認し、本文・添付・認可・pause等の条件を満たす場合だけ再開候補にする。 |
| SENDING／UNKNOWN／実行途中の状態 | 保存した要求IDでProxyを照会し、Thread／Turn IDを解決して現在状態を照会する。復旧中に新規実行要求は送らない。 |
| 対象の一致する現在照会で`inProgress` | RUNNINGへ復元し、同じ実行を監視する。有効承認待ちならAPPROVAL_REQUIRED、中断意思が残れば停止処理も継続する。 |
| 対象の一致する現在照会で`completed`／`failed`／`interrupted` | COMPLETED／FAILED／CANCELLEDへ訂正する。終了前の副作用を取り消したとは扱わない。 |
| 404、ID未取得、照会不能、Proxyの`received`／`dispatching`／`unknown`だけが判明 | UNKNOWNとして保留する。これらをGatewayからの未送信の証明にしない。 |
| 上流の明示的な開始拒否を示す`rejected` | 失敗を案内する。自動再送や元依頼のQUEUED化は行わない。 |
| 確認済みCOMPLETED／FAILED／CANCELLED | 終端記録を維持する。 |

Proxyの`phase`は受付記録であり、現在の実行状態ではない。`started`や保存済み`last_observed_status`だけでRUNNINGへ戻さない。要求IDと取得したResponse／Thread／Turnの対応、現在照会の結果・観測時刻・変更前後の状態を記録する。

**契約1.0には、送信境界通過後の要求についてGatewayからの未送信を確実に証明するAPIはない。** よってSENDING／UNKNOWNを照会結果だけでQUEUEDへ戻す規則は採用しない。これは「同じMessage IDから実行要求の送信は最大1回」とも整合する。将来の契約変更で再送方針を変える場合は別の要件改定とする。

UNKNOWNからRUNNINGへの訂正は既存実行の再観測であり、再実行ではない。終了未確認の間は同じ作業フォルダーの後続を保留し、`/resume`では解除しない。通常の解除は確実な終了確認、例外はD-11の本人による監査付き管理操作のみとする。

会話の待機一時停止フラグは依頼状態と別に永続化する。`/stop`後にGatewayを再起動しても停止フラグを維持し、`/resume`なしで待機依頼を再開しない。`/resume`は本人認可、本文・添付の再確認、並列制限、Proxyの利用可能性を迂回しない。

Codex実行状態とDiscordへの回答配信状態は分けて扱う。Codexが完了済みでもDiscord配信が失敗する可能性があるため、配信失敗を理由にCodexを再実行しない。Proxy契約1.0では途中の差分・最終回答の再取得は非対応。受信済み回答は配信処理に必要な間だけメモリに保持し、Discordへ配信する。本文・回答をDBやログへ復旧目的で重複保存しない。Gateway再起動で失った未配信部分は「取得不能」、生成自体の終了が分かれば実行状態はその確認結果として別に表示する。既にDiscordへ届いた回答はそのまま残す。

#### D-04: 本文・添付の保存と待機依頼の復旧（確定）

未送信の本文・添付はDiscordから再取得する。受付時に本文・添付の照合情報を保存し、編集・削除・取得不能・内容不一致なら実行せず再投稿を案内する。現在の利用者認可とプロジェクト登録も再確認する。

SQLiteにはID・状態・時刻・照合情報を保存し、本文や回答は重複して永続保存しない。添付の処理中の一時保存は許可し、復旧の正本として依存しない。履歴読取権限と本文取得条件を導入時に検証する。保存期間等の数値は技術設計で具体化する。

#### D-05: 同一プロジェクトの複数会話（確定）

同一会話と同一作業フォルダーは1実行に制限する。全体2実行は異なるプロジェクト間で利用する。登録時に実在ディレクトリをrealpathで正規化し、同一または祖先・子孫関係になる複数workspaceの登録を拒否する。比較はパス要素単位で行い、fooとfoobarを親子と誤判定しない。設定再読込時も検証し、不正な設定を適用しない。実行前にパスの解決先が登録時から変わっていないか確認し、シンボリックリンク変更等で検証を迂回しない。

#### D-06: 未解決事項の扱い

Q-08とD-01は制御API契約1.0を反映済み。残る確認は実運用のcwd・成果物アクセス経路と、Gatewayの結合試験である。Discord/Rustライブラリの仕様・バージョンは技術選定時に検証する。追加質問の専用回答UIは初版対象外とし、待機の検出・利用者への通知・中断経路を定義する。

#### D-07: Steerと停止の操作（確定）

Steerは初版採用済み。App Serverの公式仕様では`turn/steer`は実行中Turnへ入力を追加し、`expectedTurnId`の一致を要求する。実行中Turnがない場合は失敗する。`turn/interrupt`はTurnの中断を要求する別操作である。Steerを停止の保証として扱わない。参照: [公式App Server仕様](https://learn.chatgpt.com/docs/app-server)。

採用する操作:

- 通常投稿は次の依頼として待機させる。
- 明示したSteer操作（`/steer`）は通常の待ち行列を経由せず、指定した実行中Turnへ送る。
- 停止操作（`/stop`と停止ボタン）は実行中のAIの判断を待たず、中断APIを呼ぶ。実行枠が埋まっていても制御要求を処理できるようにする。
- 停止時はその会話の待機依頼の自動開始も一時停止する。実行中だけ止めて直後に次の依頼が動くことを避ける。`/resume`で待機の自動開始を再開する。
- Steerの対象Turnが終了済み・不一致なら失敗を案内し、次のTurnに勝手に送り直さない。送信結果不明の場合も自動再送しない。
- 中断の受付と完了を区別する。停止を確認できない場合は停止済みと表示せず、運用者への案内を出す。実行済み変更の取り消しや、独立して起動された全プロセスの停止まで保証するものではない。強制停止が必要な場合の範囲と他のProxy利用者への影響は別途決める。

`/stop`はまず対象会話のpauseと停止意思を永続化し、その後で実行中Turnの中断を試みる。pause保存に失敗した場合は停止予約済みと表示しない。

| 状況 | `/stop`の動作 |
| --- | --- |
| 実行中なし・待機だけ、または空の会話 | pauseを確定し、「待機の自動開始を停止」と表示。実行中断APIは呼ばない。 |
| SENDINGでTurn ID不明 | pauseは即時確定。保存要求IDで照会し、対象Turnを特定できたら中断を要求。未確認の間は「待機停止済み・実行の停止は未確認」と表示。 |
| RUNNING／APPROVAL_REQUIRED | 対象Turnの中断を要求し、結果を確認する。中断完了までは受付状態を表示。 |
| UNKNOWN | pauseを確定して照会する。対象を特定できない間は中断済みと表示しない。 |
| pause中の通常投稿 | 認可・容量・Proxy互換性等の受付条件を満たせばQUEUEDとして受理し、自動開始しない。 |

`/stop`と送信開始が競合した場合は、送信境界前ならpauseにより開始を防ぎ、境界通過後なら停止意思を保持して照会・中断を行う。`/resume`は停止意思の取消や中断済みTurnの再実行ではなく、待機の自動開始の再許可だけを行う。停止未確認の実行がある間は後続を開始しない。

Steerは新しい作業Turnではなく、既存Turnに対する制御操作としてID・対象・送信状態を保存する。スラッシュコマンド等にはDiscord Interaction IDを重複防止キーとして使う案。作業依頼の待機復旧ルールで古いSteerを自動実行しない。承認待ち・中断要求中・実行状態不明時に許す操作はAPI契約で定義する。

#### D-08: モデル選択と会話途中の変更（確定）

Discordでモデルを選択し、**同じ会話の文脈を保ったモデル変更を初版で実装する。** 新規会話に限定しない。Proxy契約1.0の同一Provider内モデル変更を使用し、Providerを跨ぐ変更は非対応として明示する。

変更は次の依頼から適用し、実行中Turnのモデルは変更しない。モデルと継続情報の整合性、変更失敗時の旧設定維持、会話継続、再起動後の対応復元を検証する。履歴を黙って破棄・要約置換して成功扱いしない。

Proxy公開一覧を選択UIへ用いる。同一Provider内で選択し、未対応の組合せは明示的に拒否する。モデルごとの能力・推論設定は公開一覧と検証結果に従う。技術上の制約は報告するが、モデル途中変更そのものを再び未確定扱いしない。

#### D-09: 添付の対象（確定）

入力は画像・UTF-8テキストファイル、出力は許可された成果物ファイルの返送とする。PDF・Office文書・アーカイブ・音声・動画の内容解析は初版対象外。返送ファイルを実行・展開する機能は設けない。

画像はProxyの既存入力経路を利用し、モデル能力を確認する。Discordからの取得、テキストの取込み、許可された成果物の送信はGatewayが担当する。形式検証、許可パス検証、実バイト数制限、保存期間・容量・件数は設計で具体化し、上限を超えた場合は明示する。

成果物の選定は本人の`/get <プロジェクト相対パス>`による明示指定を初版の経路とする。Codexの回答本文中のパス、変更差分、新規ファイルの検出を送信指示と見なさない。Proxyが構造化した成果物情報を提供する場合も、初版では候補表示にのみ使用し、本人の指定なしに送信しない。その情報を返す新規Proxy APIは必須にしない。

`/get`は登録済み会話スレッドで本人だけが使用できる。プロジェクトルートを基準に解決し、正規化・シンボリックリンク解決後の許可範囲、通常ファイル、サイズを検証する。読み取り時の差し替えで検証を迂回しない設計とする。無効なパスや上限超過は理由を示して拒否する。ファイル取得だけのためにCodexを実行しない。

#### D-10: 残る作業の区別

利用方針は上記で確定。残作業はProxyのAPI契約との整合、ライブラリ選定、容量・件数・保持期間などの設定値、具体的な画面・状態遷移・テスト設計である。既定値は設計案として根拠を記録する。許可する実プロジェクトのパスやDiscord ID等の導入情報は稼働設定時に必要となる。

#### D-11: 解消不能なUNKNOWNの管理用解除

ローカルの本人用運用コマンドとして、指定依頼のUNKNOWNによるGateway側workspace保留を解除する機能を設ける。通常のDiscord操作や`/resume`からは利用できない。

- 対象依頼ID・workspace・最終照会結果と「実行が残っている可能性」を表示し、理由入力とリスクの明示確認を要求する。コマンド名・確認方式は技術設計で固定する。
- UNKNOWNレコードを削除せず、COMPLETED等へ変更しない。操作者・理由・時刻・対象・確認内容・解除事実を永続化する。記録失敗時は解除しない。
- 指定UNKNOWNが保持する保留だけを解除する。別の実行・UNKNOWNの保留、会話pause、認可・並列・Capabilityの条件は維持する。
- 元の依頼は再送しない。自動解除・有効期限による解除は行わない。再起動後も解除の監査記録を維持する。
- Proxy側の同一Thread競合拒否・権限・実行記録には触れない。元ThreadがProxyで保留されていれば、別会話の利用またはProxy側の運用確認が必要となる。
- 解除は実行の終了確認ではなく、本人が未確認の競合リスクを引き受ける例外である。後から元実行がRUNNINGと判明した場合は観測を記録し、新規開始を再び保留して本人に通知する。
