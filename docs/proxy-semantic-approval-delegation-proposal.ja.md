# 操作の意味に基づく依頼中承認委任 — Proxy調整案

版0.1 / 2026-09-17 / Tane Channel Technology

状態：利用者から方向性の承認を受けたGateway側の提案。Proxyとの具体契約・実現性・数値条件は未合意。実装・常駐有効化の指示ではない。

基準：[現行API 0.6](../../codex-hoshikage-proxy/docs/mcp-approval-api-v06.ja.md)、[Gatewayの現行内部設計](mcp-approval-layered-gateway-design.ja.md)。本案で既存APIや既存許可の意味を変更しない。

## 1. 解決したい問題

利用者が一つの作業を任せても、同じ目的・作用の操作ごとに承認が繰り返され、作業を任せる利点が失われる。ツール名や引数の完全一致だけでは、対象や指定方法が変わる同種の操作を扱えない。一方、全ツールの意味を事前に解析することを汎用機能の前提にはしない。

要求は「利用者が具体的な操作範囲を一度許可し、同一依頼中の後続操作がその範囲に含まれるかをLLMが判断する」こと。特定サイト・サービス・業務を製品要件に含めない。個別ユースケースは実地試験に利用できるが、中核の分岐や成立条件にしない。

これはAIによる判断委任であり、操作の安全性や誤判定ゼロを保証する仕組みではない。厳密な条件照合、管理者の禁止規則、単発承認とは区別する。

## 2. 方向性として合意した要件

| ID | 要件 |
| --- | --- |
| SD-01 | 利用者が確認した目的・対象・許容する作用・除外する作用で委任範囲を定義する。「同じ種類」「安全な操作」だけの説明で承認を取らない |
| SD-02 | 現在の実操作・実引数と、今後任せる範囲を分けて表示し、明示選択で委任する。単発許可やポリシーの選択だけから委任を自動作成しない |
| SD-03 | 同一依頼中、範囲内と判定した後続操作は承認画面を繰り返さず進められる。引数が変わるだけでは自動的に再確認しない |
| SD-04 | 範囲外・判断不能は人へ確認する。管理者規則で禁止された操作は単発承認でも迂回しない。既存の完全引数・対応付け要件を満たさない場合も許可不可 |
| SD-05 | 実行LLMの自己申告だけで許可しない。独立した判定処理が実呼出しと根拠を照合する |
| SD-06 | 別利用者・別依頼・別並列Runに流用しない。完了・停止・取消・追加指示・Steerで失効させる。承認ボタンの押下は追加指示ではない |
| SD-07 | 表示・単発承認・判断委任を分離する。未選択の実行や他クライアントの設定・権限へ波及させない |
| SD-08 | 誤判定の可能性、委任範囲、失効条件を利用者へ説明する。許可一覧・個別取消・照会可能な監査記録を提供する |

「依頼」はGatewayの認証済み依頼をProxyのResponse／Runと対応付けた単位。会話全体の恒久許可ではない。既存ツール単位の依頼中許可も本案の意味ベース委任へ自動変換しない。

## 3. UI案

現在の操作内容と忠実な引数表示を維持し、その下に委任範囲を表示する。例えば、汎用的な例として：

> 今回の操作：表示情報を更新する
>
> この依頼中に任せる範囲：今回指定したサービスの情報表示画面で、情報の再取得・表示更新を行う。
>
> 含めない操作：投稿・購入・削除・設定変更。
>
> 後続操作がこの範囲内かをAIが判断します。誤判定の可能性があります。

基本ボタン：**［この範囲を依頼中は許可］［今回だけ許可］［拒否］**。

- 「今回だけ」は現在の実呼出しのみ。「この範囲」は現在の実呼出しと後続の範囲内操作が対象。現在の操作も範囲内と確認してから委任候補を出す。
- 候補を作れない・機能未対応の場合は理由と単発／拒否を提示する。実際に機能しない一括許可ボタンは出さない。
- 範囲外なら何が違ったか、判断不能なら何の情報が不足したかを短く示す。既存委任の拡張は別の明示承認とし、単発許可で範囲を学習・拡張しない。
- 公開範囲と意味評価は独立。公開可能な内容は元の会話に表示し、秘密・長文等の本人向け表示は現行契約に従う。
- 判定中は押下をACKし、必要な待機状態を示す。内部キャッシュ更新で画面・確認済み内容を交互に失効させない。
- 自動許可ごとの定型投稿はしない。許可一覧と監査から適用範囲・回数・取消状態を確認できるようにする。
- 人が読む時間を判定処理のタイムアウトと混同しない。確認中の内部更新だけを理由に短時間で承認を無効にしない。

## 4. 責務境界

| 担当 | 責務 |
| --- | --- |
| Proxy中核 | 実call・完全引数・実行の対応付け、認可、委任資源と版、適用の競合制御、上流承認仲介、取消・失効・復旧・監査 |
| Proxyの明示選択ポリシー拡張 | 委任候補の作成、LLM判定、根拠の検証、固定の禁止／個別確認規則との合成 |
| コンテキスト取得adapter | ブラウザー等の操作対象・状態・証拠を取得し、由来と鮮度を示す。必要な場合に利用する拡張であり、全ツール対応を中核の必須条件にしない |
| Gateway | Discord本人認可、実行との対応、範囲と操作の表示、明示選択、拒否・取消、配信／押下結果の復旧 |

Discord IDやBot tokenはProxyへ渡さない。Gatewayにツール意味解析やサーバー内ファイル探索を持ち込まない。判定LLMは操作用のMCP権限や承認書込み権限を持たず、判定結果だけを返す構成を推奨する。

## 5. 判定処理と証拠 — 推奨設計

1. Proxyが現在のcallと引数を確定し、適用中の固定規則を先に検査する。
2. ポリシー拡張が委任候補を作成する。候補はモデル由来の提案であると区別し、利用者が表示した具体範囲を承認するまで無効。
3. 利用者の承認を、候補版・表示指紋・実行境界に結び付けて保存する。
4. 後続callごとに、承認範囲、実ツール定義、実引数、必要な画面／対象情報を独立した判定処理へ渡す。
5. 構造化結果 `範囲内 / 範囲外 / 判断不能` と短い根拠・参照証拠を取得する。数値の自信だけを許可根拠にしない。自由文や壊れた応答は判断不能。
6. 適用直前に、call・引数・依頼世代・委任版・設定世代・必要な証拠の有効性を再確認し、範囲内の結果だけを上流承認へ適用する。

実行LLMの目的説明やツールのelementラベルは補助情報であり、操作対象を証明しない。ページ本文・ツール出力・取得資料は信頼できない入力で、委任やポリシーを変更する命令として扱わない。内部思考の保存ではなく、判断の結論・短い根拠・証拠参照を監査する。

ブラウザーの場合、URL・ページ／タブ識別子・対象要素・遷移先・フォーム等の必要性はadapterで定義する。Proxyが現在取得できると仮定しない。対象が差し替わる可能性、並列ページ操作、判定から実行までの変化を検出／拘束できる範囲を実証する。根拠が古い・取得不能・対応不明なら意味ベースの自動許可をしない。画面情報を毎回すべて必要とするのではなく、当該範囲の判断に必要な最小証拠を定義する。

## 6. ライフサイクル・障害・競合

- 候補・有効な委任・取消済み／失効済みを区別する。利用者承認後の範囲は不変とし、変更は新しい版への明示承認とする。
- 許可はinstance／復元世代、認可主体、Run／Response、依頼内容世代、ポリシー版に拘束する。個別判定はcall ID、引数指紋、委任版、根拠参照、判定モデル／設定版も照合する。
- 停止・取消・Steer受理時は新たな許可適用を止める。判定中の旧結果を破棄する。既に上流承認送信を開始した処理まで取り消せるとは表示せず、送信開始との境界を契約化する。
- 複数の委任をLLMが組み合わせて承認範囲を拡張しない。まず1操作に1つの有効な委任が適用できる設計を推奨する。
- 再起動後は同じIDを照会する。委任・設定・実行の対応を確定できない間は自動適用しない。正式復元での世代不一致は既存の復元隔離を継承する。
- 判定には有限の処理期限・同時数・入力／出力上限・費用上限を設け、停止／拒否経路を塞がない。具体値は未確定。超過は判断不能として案内し、黙って広い許可へ切り替えない。
- 上流承認送信結果不明は同一操作を照会し、証拠なしで再送しない。判定失敗やUI配信失敗を元のAI実行の再実行で補わない。

## 7. APIで必要な情報・操作

以下は論理要件で、エンドポイント名・JSONキー・新バージョン番号の確定案ではない。

| 契約領域 | 必要な内容 |
| --- | --- |
| Capability | 対応有無、選択可能ポリシー、取得可能な根拠、制約、上限、未対応理由 |
| 選択と実効設定 | 表示指定とは独立した明示選択、適用済みのモデル／規則／設定世代。選択は委任の作成ではない |
| 委任候補 | 不透明ID、版、目的・対象・許可作用・除外作用、表示情報、現在のcallとの対応、有効性 |
| 承認操作 | 単発／委任／拒否の区別、期待する候補版・表示指紋・実行境界、冪等キー、結果照会 |
| 委任一覧・取消 | 状態、範囲、実行、適用回数、失効／取消理由、取消結果不明の照会 |
| 判定・監査 | callとの対応、結論、短い理由、証拠参照、委任とモデル／規則版、適用状態 |
| エラー | 範囲外、証拠不足、モデル利用不可、期限／容量超過、禁止、古い画面、失効、結果不明の区別と再操作可否 |
| 永続化と保持 | 候補・委任・判定・操作結果それぞれの保存期限、照会保証、個人情報の保持・削除方針 |

API 0.6の既存policy識別子・grantの意味を変更しない。新ポリシー／契約を明示的に交渉し、旧Gatewayは既存の表示・単発・既存turn許可を維持する。新機能非対応を製品全体の停止条件にはしないが、新機能を要求したRunを黙って別ポリシーで開始しない。

## 8. Proxy側に回答・実証を依頼する事項

| ID | 確認事項 | Gateway側の推奨 |
| --- | --- | --- |
| P-01 | 独立判定をどの実行経路・モデルで動かせるか。認証、追加費用、文脈隔離 | Proxy運用設定で明示し、実行側と判定処理を分離。同じモデルの別コンテキストでも、同じ誤りをする可能性を保証外として明記 |
| P-02 | callと画面／対象情報をどう対応付けるか。上流から足りない情報は何か | 取得・拘束可能な根拠を実測。adapter等の追加が必要なら責務とAPIを提示 |
| P-03 | 委任候補の生成、許可対象となる操作群、固定禁止規則 | ツール横断も概念上可能とするが、対象ツール／接続先の範囲を明示し、未対応経路へ勝手に広げない |
| P-04 | 判定後の対象変更、並列call、停止／Steerとの競合 | 適用直前の照合と旧判定失効。原子性を保証できない区間も明記 |
| P-05 | 再起動・復元・モデル／プロンプト／規則変更時の委任 | 同一性を検証できるときのみ復旧。互換性不明の変更で既存委任を自動流用しない |
| P-06 | レイテンシ・容量・費用・保持・根拠の秘匿 | 運用上限と通常時の応答目標を測定して提案。生の認証情報は判定器へ送らない |
| P-07 | 新policyとAPI差分・旧版互換・Gatewayの表示契約 | 具体的なJSON例、状態遷移、エラー、上限、受入条件を提示して接続レビュー |

判断材料を得られない問題を、利用者に毎回同じ承認を求める運用だけで「完成」と扱わない。実現できない範囲は明示し、必要な上流拡張または別の実現方法を提案する。

## 9. 受入条件

| ID | 試験 | 期待結果 |
| --- | --- | --- |
| S-A01 | 同目的・同作用で対象や引数を変えた複数操作 | 最初の委任後、根拠が揃った範囲内操作は確認を繰り返さない |
| S-A02 | 同じツール名で更新から投稿・購入・削除等へ作用変更 | 元の範囲にない操作を自動許可しない |
| S-A03 | 異なるツールで同じ意味の操作 | 明示された対象ツール群・証拠・規則に合う場合のみ適用。名称一致だけに依存しない |
| S-A04 | ラベル偽装、ページ／ツール出力からの許可変更指示 | ラベルや命令文を権限根拠にしない |
| S-A05 | 情報不足、モデル停止、不正応答、予算／期限超過 | 判断不能を示し、可能なら単発／拒否。無条件許可しない |
| S-A06 | 判定後の引数・ページ・対象変更、並列操作 | 古い判定を別の実呼出しへ適用しない |
| S-A07 | 停止・取消・追加指示・Steer・終端との競合 | 新規自動許可を停止。送信済み境界を正しく表示 |
| S-A08 | 別利用者・別会話・並列Run・次の依頼 | 委任を流用しない |
| S-A09 | 再起動、正式復元、押下／送信後の通信切断 | 同じ永続IDで照会し、未知の承認やAI依頼を再送しない |
| S-A10 | 単発許可、既存turn許可、未選択実行、旧クライアント | 委任へ昇格せず、既存の契約と禁止規則を維持 |
| S-A11 | 人が時間をかけて確認、内部キャッシュ更新、複数ページ | 内容が消えず、同じ対象の画面が不要に切り替わらず、内容確認後に承認できる |
| S-A12 | 実モデル・実MCP・実Discordで複数操作を継続 | ボタン押下だけでなくツール完了・目的達成を確認。モック成功を実用性の証明としない |

肯定例だけでなく紛らわしい否定例・攻撃入力を用意する。モデル／規則変更時も回帰評価し、自動許可の誤りと過剰な再確認を双方計測する。許容基準は実証前に双方で合意し、有限の試験成功から誤判定ゼロを主張しない。

## 10. 進め方

1. 本案の責務・要求とP-01〜07をProxy側でレビューする。
2. 読み取り・模擬判定中心の実証で、独立判定と根拠取得／call対応付けが成立するか確認する。常駐の自動許可は有効にしない。
3. 双方の要件・詳細設計・API契約・受入条件を完成させ、接続レビューを解消する。
4. 製品実装、障害・競合試験、許可された実環境での受入を進める。
5. 利用者向け説明と運用設定を整えてから、常駐有効化を別途行う。
