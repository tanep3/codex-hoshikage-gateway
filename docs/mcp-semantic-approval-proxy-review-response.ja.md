## 判定

方向性と責務分担に合意し、詳細設計・隔離した実現性検証へ進める。具体API・初期対象・数値条件・製品実装・常駐有効化へのGoではない。Proxy回答のP-01〜07は設計方針への回答であり、実証済みの回答とは区別する。

## 受け入れる整理

- 目的は同一依頼中の反復承認と待ち時間の削減。対象範囲を明示した製品機能として、初期から取消・復旧・監査・対象照合を備える。
- scopeをProxyが発行し、認証の信頼境界、会話、Run、入力世代、稼働／復元世代を対応付ける。自己申告IDだけによるクライアント隔離は保証しない。
- 禁止、必ず個別確認、委任の判定、単発確認を区別する。固定除外は新しい明示選択ポリシーの規則とし、標準API全体へ拡張しない。
- 全条件を現在の証拠で機械的に確認できる場合はLLM不要。自然文条件が残る場合は独立判定する。過去のLLM肯定結果や同一tool名だけでは高速経路へ通さない。
- 初期は同一Runで旧ツール単位の包括許可と新しい意味委任を混在させず、単発許可は併用する。新委任の取消が旧許可によって実質無効になることを防ぐ。
- Gateway再起動は照会で復旧し、Proxy再起動・正式復元では旧委任を失効させる推奨を受け入れる。権限失効と元の実行の成否は別に表示し、再実行しない。
- 独立判定・必要な対象証拠・監査を後回しにしない。ただし全ツール解析や任意環境の完全な安全性証明を開始条件にはしない。

## 詳細設計で具体化する焦点

### 1. 固定除外の判定が意味委任を空洞化しないこと

未知の作用を、除外に当たらないと推測して通さない方針は妥当。ただし「クリックの作用を全て事前に機械的に確定できないから、クリック全般が対象外」という結論では、今回の目的に届かない。

初期対象の連続操作について、(a) 固定規則を適用する証拠、(b) 機械照合する条件、(c) LLMに残す意味判断を具体例で分けて提示してほしい。安全性の意味判断を全て前段で完了させる設計にも、LLMの説明だけで除外を解除する設計にも寄せない。成立しない場合は、必要なadapter／上流拡張と、実用上の制限を示す。

### 2. 初期対象を実際の連続操作で選ぶこと

タブ一覧や検索だけの成功では、同種クリックで確認が続く問題の改善を受入済みにしない。特定サイトを製品要件にせず、例えば「対象の変わる表示更新・表示切替などを含む連続閲覧」を試験候補とし、現在困っている個別ユースケースは実地試験に位置付ける。

実現性検証では対象候補と仮説を固定する。製品受入の合格値は、その予備測定を根拠に受入試験前に固定し、受入結果を見て緩和しない。承認回数、待ち時間、誤許可、過剰な再確認、費用を別々に測定する。

### 3. 人が承認する範囲を読み取れること

現在の実引数、将来の許可範囲、除外範囲、機械照合とAI判断の違いを区別して表示する。「今回のサービス」のような未解決の指示語だけにしない。根拠が足りない時は、何を確認できず単発へ戻ったかを説明する。毎回同じ説明を連投する動作を避ける。

## 次にProxyから受け取りたいもの

1. 初期対応の操作群と証拠取得経路の表。除外／機械照合／LLM判断の境界を含む。
2. 独立判定器の候補経路と、認証・費用・秘密情報・実行権限隔離の実証計画。
3. 対象の変化、停止、Steer、再起動を含む状態遷移と、保証できない境界。
4. 上記の実証を経たAPI差分、全応答例、上限・保持、受入条件。

Gatewayはこれらを受けて表示・状態管理・取消・復旧の具体設計を照合する。未合意のフィールド名で実装を先行しない。本回答ではコード・設定・常駐環境を変更していない。
