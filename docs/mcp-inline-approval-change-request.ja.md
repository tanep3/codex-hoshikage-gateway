# MCP承認を最初のカードで完結させるための契約調整

2026-09-16。利用者から実装指示を受けたUI変更。表示先は利用者が「元の会話にまとめる。Proxy側の公開用情報も調整する」と確定済み。DMへの変更は行わない。現行API 0.3の機能として扱わない。以下はProxyとの調整案であり、未合意のフィールドをGatewayが推測して使用しない。

## 利用者に提供する動作

承認が必要になったら、依頼元の会話に操作内容と選択肢をまとめて表示する。「操作詳細」を押して別画面を開くことを通常フローの必須手順にしない。基本の選択肢は「この依頼中、このツールを許可」「今回だけ許可」「拒否」。ターン限定許可の対象外では最初の選択肢を表示しない。許可一覧・取消は承認とは別の管理操作として `/mcp` に分ける。

「操作内容」は、ツール名だけではなく、何を・どの対象に行うかを判断できる説明。モデルが書いた説明と、実際のツール呼出しから取得した情報を混同しない。常時許可のツールに、UI試験の都合で新たな確認を要求しない。

## 現契約でできないこと

API 0.3の `operation.arguments` は `disclosure=requester_only`。通常のDiscordメッセージに本人限定のephemeral表示を自発送信することもできない。このため、現レスポンスをそのまま公開カードへ移す実装はしない。現契約の秘密保持条件を無言で変更しない。

## Proxy側への調整要求

1. 元の会話に表示してよい操作情報と、本人限定の実引数を区別して提供する。具体フィールド・Capability・バージョンはProxy回答で確定する。
2. 公開情報には判断に必要な操作・対象・制限を含める。秘密情報を含むURL、トークン、任意コード内の秘密などを単にGatewayの文字列置換へ任せない。公開できない情報や省略を明示し、判断に不足する要約だけで承認可能にしない。
3. 公開情報を元のinteraction、Response/Turn、revision、scope fingerprintへ確実に結び付ける。表示した内容が変わった後、旧カードから許可できないこと。未知・不整合・期限切れでは許可を送らない。
4. 操作説明は安全性保証ではない。ターン限定許可の適格性と、公開可能性を独立に判定する。実コードを伴う高危険度操作は従来どおり個別確認とする。
5. 公開情報だけでは判断できない場合の例外フローを契約化する。本人限定の補足確認を必要とする場合は理由を最初のカードに明示する。情報欠落を理由に未知の操作を許可しない。
6. 単発／ターン許可の既存返信・失効・取消・冪等性は維持する。直接ボタンからの承認でも、表示確認をDBへ固定し、押下時にProxyから同じ内容・範囲を再照合する。

## Gatewayの実装・受入

公開可能な操作説明と許可ボタンを同じカードの同じ表示版で送る。詳細取得後に説明を別投稿する順序にしない。表示確定前のボタンや、他人・別会話・古い表示・世代不一致・秘匿により判断不能な操作から許可できないことを確認する。

実引数はDBへ保存しない。公開・本人限定の区別、表示digest、再起動時の照合、送信結果不明、単発とターンのbody、二重押下、対象外ツールの2択、長い操作情報の扱いをテストする。モックの後に実Proxy・利用者による実Discordボタン操作を確認する。

契約確定後、要件書・システム設計・詳細設計・日英利用者マニュアルをまとめて置換する。未対応Proxyで新UIが動くと案内しない。


## 0.4レビューへの回答と利用者の追加判断

Proxyの0.4接続レビュー案を照合した。利用者は検索語・アクセス先URL等の操作対象を元会話へ表示する方針を明示承認し、認証情報・秘密入力・任意コードは補足確認へ分けるとした。返答の全文と具体的な契約反映依頼は [接続レビュー](mcp-inline-approval-api-review.ja.md) を参照。HTTPと表示トークンの境界に接続上の異論はない。具体rendererの契約反映後にGateway実装へ進む。
